# Workflow editor performance: JointJS vs React Flow in React

Report for the editor-canvas benchmark in [bench-editor/](bench-editor/README.md). This is
separate from the landing-page comparison of variants A–D ([README.md](README.md),
[COMPARISON.md](COMPARISON.md)).

**Question.** If Texera's frontend moves to React, does rendering the workflow editor
through React (React Flow) cost performance on large workflows, compared with keeping
JointJS and hosting it inside React?

**Short answer (full-speed profile).** No. React Flow is faster than JointJS *as Texera
configures it today* on every speed metric at every size. With each library's own
large-graph settings, JointJS renders first fastest and React Flow is fastest at the
operation that matters most while a workflow runs (repainting operator statistics), and
uses the least memory. React Flow's one real cost is memory when nothing is culled:
~2.7× JointJS's JS heap at 5,000 operators. Mid-range and low-end profiles are pending
(see [Weaker machines](#weaker-machines)).

## What was measured

Same synthetic graph in both libraries, shaped like a Texera workflow: operators in DAG
columns (25 per column), each a 180×64 box with name, status line, one input and one
output port; ~1.33 links per operator. `@joint/core` 4.3.4 and `@xyflow/react` 13.0.2 in
React 19, production build, headless Chrome 155. Each run is a fresh page.

| Case | Settings |
| --- | --- |
| JointJS (default) | Texera's editor today: synchronous paper, approximate z-sorting, no culling |
| JointJS (optimized) | async + frozen rendering, `viewManagement` (lazy views, dispose hidden) + `cellVisibility` culling, status rounds batched with `freeze`/`unfreeze` |
| React Flow (default) | controlled flow (`useNodesState`), memoized custom node, everything mounted |
| React Flow (optimized) | same + `onlyRenderVisibleElements` |

| Scenario | What it does |
| --- | --- |
| Initial render | time until the canvas DOM stops changing |
| Pan | 120 frames moving the viewport at 100% zoom |
| Zoom-out | 60 frames to 15% and back (~800 operators on screen at 15%) |
| Drag | 120 frames moving one operator |
| Status update | 20 rounds relabeling every operator (Texera's execution statistics), time until painted |

Memory is per run frame via Chrome's `performance.measureUserAgentSpecificMemory()`, after
a forced GC, minus an empty-page baseline, so it is the graph's own cost. "Blocking time" is
Total Blocking Time over the whole run: long-task time beyond 50 ms, i.e. how long input
would have been frozen. Medians of 3 runs. Full method: [bench-editor/README.md](bench-editor/README.md).

## Findings

1. **React is not the bottleneck.** React Flow (default) beats JointJS (default) at every
   size: 3× faster first render at 5,000 operators (916 vs 2,637 ms), 13× faster status
   updates (189 vs 2,435 ms), and 60 fps zoom where JointJS drops to 8 fps. React Flow
   updates only what changed, through memoized node components; the default JointJS paper
   re-renders each cell synchronously as its attributes change.
2. **With both libraries tuned, each wins different metrics.**
   - JointJS (optimized) has the fastest first render (163 vs 387 ms at 5,000).
   - React Flow (optimized) has the fastest status updates (33 vs 101 ms at 5,000), the
     least input blocking (0.3 vs 1.1 s) and the least memory (10 vs 27 MB).
   - Both hold 60 fps panning and dragging at every size.
3. **React Flow's cost is memory when nothing is culled.** At 5,000 operators the default
   React Flow graph takes 143 MB of JS heap vs 52 MB for JointJS (each React node keeps a
   component instance, props and fiber). JointJS has the larger DOM (18 vs 9 MB, SVG text
   is heavier). With culling, React Flow drops to ~10 MB; JointJS keeps a model object per
   cell even when its view is disposed, so it stays at ~27 MB.
4. **No leaks.** After all scenarios, memory grows by at most ~3 MB in any case (JointJS
   gains 2–3 MB; React Flow stays flat).
5. **Today's Texera editor settings are the main weak point, not the library.** Relabeling
   1,000 operators takes ~214 ms per round with the current settings vs 23 ms with
   JointJS's own async rendering and culling. Turning those on is a cheap fix in the
   current Angular app, independent of any migration.

What changes on a slower machine:

- **The ranking holds, and the gaps widen.** At 5,000 operators JointJS (default) needs
  11.3 s to render and 10.8 s per status round, with zoom at 2 fps and drag at 6 fps: this
  is roughly what Texera's current editor would do on such a machine. React Flow (default)
  needs 3.1 s and 664 ms.
- **Optimized React Flow is the only case that stays smooth everywhere:** 60 fps pan and
  drag at 5,000 operators, 120 ms status rounds, 2.7 s of total input blocking over the
  whole run (vs 9.5 s for optimized JointJS).
- **Optimized JointJS still renders first fastest** (665 ms vs 1,417 ms at 5,000), but
  panning drops to 23 fps there: creating views lazily as they scroll into sight costs
  more on a slow CPU.
- **Memory is independent of CPU speed**, as expected: the figures match the full-speed
  profile within a few MB.

## Svelte and Solid (apache/texera#9387)

A comment in the [framework discussion](https://github.com/apache/texera/discussions/9387)
argues that the canvas requirement (R3) should not rule out Svelte or Solid, and that
React's re-render model costs the most exactly where Texera is busiest (live operator
status, streaming updates), in both speed and memory. It asks for a canvas prototype in
Solid or Svelte next to the React one, with a perf and memory profile under live execution.

What the data above already says about those claims:

| Claim | Assessment |
| --- | --- |
| Svelte has a real canvas library | **Valid.** Svelte Flow is official, from the xyflow team; 2.0.2 shipped the same day as React Flow 13.0.2. ~374k weekly downloads. |
| Solid has a real canvas library | **Weaker.** `@dschz/solid-flow` is a one-maintainer community port (~2.8k weekly downloads): 0.2.x targets Solid 1, the 1.x line is a prerelease that needs Solid 2 (released 2026-11-17). |
| React re-rendering is slow for live status updates | **Not supported for the canvas so far.** React Flow repaints 5,000 operators' status in 189 ms (33 ms with culling); JointJS, which has no virtual DOM, takes 2,435 ms with Texera's current settings and 101 ms optimized. Update batching and culling matter more than VDOM vs no VDOM. Not yet compared against Svelte/Solid; see below. |
| React holds more memory | **Valid when nothing is culled:** 143 MB vs 52 MB JS heap at 5,000 operators (React Flow vs JointJS). With culling React Flow is the smallest (10 MB). React's own runtime baseline is 2–5 MB. No growth over the scenarios (sessions of hours were not tested). |
| The Yjs layer is portable TypeScript | **Valid.** The shared model (`SharedModel`, `WorkflowGraph`) has no JointJS references; the coupling is in the view and glue code. |

**Being tested now.** The benchmark adds Svelte Flow 2.0.2 (Svelte 5.58) and solid-flow
0.2.6 (Solid 1.9.20), with the same operators and scenarios, each mounted by its own
framework (no React on those pages) and each using its idiomatic fine-grained update path:
per-operator `$state` data in Svelte, store paths in Solid (`setNodes(i, "data",
"status", …)` inside `batch`). Two additions for the comment's specific ask:

- **Live execution** scenario: 300 frames where a rotating 10% of the operators get new
  statistics every frame while the user pans (each operator updates ~6×/s).
- **JS downloaded** per run (framework + canvas library), next to the memory figures, and
  line counts per canvas implementation.

**Bundle and code size** (from the production build; `node bench-editor/scripts/bundles.mjs`):

Shared harness (run page, loaded by every run): 3.4 KB JS

| Canvas | JS (gzip) | CSS (gzip) | Canvas code (lines) |
| --- | --: | --: | --: |
| JointJS (in React) | 190.3 KB | 0.0 KB | 148 |
| React Flow | 150.6 KB | 2.6 KB | 110 |
| Svelte Flow | 74.1 KB | 2.8 KB | 81 |
| solid-flow | 58.2 KB | 2.5 KB | 105 |

JS is what a page loads for that canvas: framework runtime + canvas library + adapter, gzipped. "Canvas code" is the implementation of the same operator node and canvas wiring in each framework (the shared runner, graph and metrics code is not counted).

**Findings**

1. **The real-time layer is cheap here too.** Yjs plus the binding cost 77–169 ms of CPU per
   30 s session in every case: under 5% of the main thread's work at 30 operators and under
   2% at 300. What costs is drawing the changes.
2. **Texera's current editor settings break down at sizes people build, on this machine.**
   At 30 operators: 21 frames over 50 ms and 0.8 s of input blocking. At 100: 38 fps and
   9.7 s of blocking in a 30 s session. At 300: 10 fps, the main thread blocked for the
   whole session, statistics 24.5 s behind and remote drags 7.6 s behind. The stalls come
   with the statistics: every 500 ms each operator is re-rendered synchronously, three times
   (one `attr()`, one `portProp()` per port). The local user's own drag still shows within a
   frame between those bursts.
3. **JointJS with its own large-graph settings** (async rendering, culling) is smooth at 30
   operators and close at 100 (57 fps, 28 long frames, 6 ms of blocking, statistics 89 ms
   behind), but at 300 drops to 50 fps with 31 long frames, 2.7 s of blocking and
   statistics 200 ms behind, using 10.9 s of CPU: about twice React Flow or Svelte Flow
   with culling.
4. **React Flow and Svelte Flow hold 57–60 fps with no input blocking at every size**, and
   statistics reach the screen in 14–45 ms. With culling, at 300 operators: 5.8 s (React
   Flow) and 5.1 s (Svelte Flow) of CPU per session, ~5 MB. React itself is 0.6 s of React
   Flow's 5.8 s.
5. **solid-flow is fine up to 100 operators**; at 300 it has 29 long frames and its culling
   does not help (10.7 s of CPU and 17–23 MB either way), as in the stress tests.
6. **Memory is small for everyone at these sizes**: 2–25 MB (JS + DOM) beyond the empty page.

**Is it JointJS, or how Texera updates it?** Most of the JointJS cost is `portProp()`, which
re-renders an operator's ports for each row count. With `?labels=element` the row counts are
texts of the operator itself, written in the same single `attr()` call (a change Texera could
make today). JointJS only, same profile and sessions

7. **Both Texera-side fixes together make JointJS as smooth as the Flow libraries at 100
   operators**: 59 fps, no long frames, no blocking, 5.2 s of CPU (React Flow: 4.2 s,
   Svelte Flow: 3.4 s with culling). Either fix alone is not enough: the label change on
   today's synchronous paper still blocks input for 2.2 s at 100 and 11.6 s at 300.
8. **At 300 operators the library itself shows**: fully tuned JointJS still has 30 long
   frames and 0.5 s of blocking, using 8.8 s of CPU against 5.8 s (React Flow) and 5.1 s
   (Svelte Flow) with culling.

## Caveats

- **Headless Chrome rasterizes without the GPU.** SVG repaints are expensive there, so the
  zoom-out numbers likely overstate JointJS's disadvantage; render, status-update and memory
  numbers are mostly CPU work and carry over better. For real-window numbers, open
  `http://localhost:4180/?autostart=1` in a normal Chrome window and keep it in front.
- **Light operators in the stress tests.** The canvas and collaboration runs use a box with
  a name, a status line and two ports; the realistic session uses the Texera-like operator.
  Real operators raise absolute costs for every library.
- **Rendering layer only.** The Yjs model, app shell and the rest of the workspace are not
  part of these numbers; neither are React Flow features Texera would add (custom edges,
  overlays), nor JointJS tools (link buttons, highlighters).

## Reproducing

```sh
npm run build -w bench-editor && npm run preview -w bench-editor
node bench-editor/scripts/run-headless.mjs 100,500,1000,2000,5000 3                          # full speed
taskset -c 0-3 node bench-editor/scripts/run-headless.mjs 100,500,1000,2000,5000 3 --cpu=4   # mid-range
taskset -c 0-1 node bench-editor/scripts/run-headless.mjs 100,500,1000,2000 3 --cpu=6        # low-end
node bench-editor/scripts/report.mjs bench-editor/results/<file>.json
```

Raw results (every run, every metric) are in `bench-editor/results/`.
